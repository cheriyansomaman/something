# Senior Java Developer Interview — Live Coding, Set 3

Ten additional live coding questions, complementary to the 24 in Sets 1 and 2 (no overlap).
Each includes **answer hints** describing the expected approach, pitfalls to watch for, and follow-ups.

---

**LC13. Implement an LRU cache from scratch with O(1) `get` and `put` (fixed capacity, evict least recently used). No `LinkedHashMap` allowed.**
> **Hints:** `HashMap<K, Node>` + hand-rolled doubly linked list (head = most recent, tail = eviction candidate); on `get`, unlink node and move to head; sentinel head/tail nodes eliminate null checks; watch for the classic bugs: forgetting to update the map on eviction, broken links when moving the head itself. Follow-ups: make it thread-safe (coarse lock vs segment locking — and why per-node locking doesn't work with a shared list), then compare with `LinkedHashMap(capacity, 0.75f, true)` + `removeEldestEntry` to check they know the shortcut exists.

**LC14. Write a `Comparator<String>` for semantic version strings: `"1.2.10" > "1.2.9"`, `"1.0" == "1.0.0"`, handle a `-SNAPSHOT`/pre-release suffix ordering before the release.**
> **Hints:** Split on `.`, compare numerically segment by segment (`Integer.compare`, not string compare — that's the whole point of `"10" vs "9"`); missing segments treated as 0; pre-release: strip suffix, compare base versions first, release > pre-release of the same base (SemVer rule); pitfalls: `a - b` overflow idiom, `NumberFormatException` on garbage input (decide: throw vs lenient); must satisfy comparator contract (transitivity) — ask them how they'd test that (e.g., sort a shuffled known list, property-based testing).

**LC15. Merge K sorted iterators lazily: implement `Iterator<T> mergeSorted(List<Iterator<T>> iterators, Comparator<T> cmp)` that yields elements in global sorted order without materializing the inputs.**
> **Hints:** `PriorityQueue` of (currentValue, sourceIterator) entries; `next()` polls the min, then re-offers the source's next element if it has one — O(log k) per element, O(k) memory regardless of stream length; subtleties: `hasNext` must not consume, so buffer one element per source; empty iterators filtered at init; comparator must not be applied to the wrapper accidentally. Follow-ups: where is this pattern used for real (merge phase of external sort, compacting SSTables/log segments, merging per-partition results)?

**LC16. Aggregate three downstream services in parallel with `CompletableFuture`: call `pricing`, `inventory`, and `reviews` for a product; return a combined DTO. Requirements: total budget 800 ms, `reviews` is optional (fallback to empty), the other two are mandatory.**
> **Hints:** Three `supplyAsync` on an explicit executor (not the common pool — blocking I/O); `reviews` gets `.completeOnTimeout(empty, ...)`/`.exceptionally(t -> empty)`; combine via `thenCombine` chaining or `allOf` + joins after completion; overall deadline with `orTimeout` on the composed future; key senior signals: distinguishing per-call vs total budget, not calling blocking `get()` inside a continuation, cancellation awareness (`orTimeout` doesn't cancel the underlying HTTP call — what does?). Follow-up: rewrite with virtual threads + `StructuredTaskScope` and compare readability.

**LC17. Implement a basic arithmetic expression evaluator: `evaluate("3 + 5 * 2 - 8 / 4")` → `11` (integer math, correct precedence). Then add parentheses support.**
> **Hints:** Two-stack algorithm (values + operators, apply while top of operator stack has ≥ precedence) or convert to postfix (shunting-yard) then evaluate; single left-to-right pass with "last sign + pending multiplication/division" also works for the no-paren version; pitfalls: division order (`b / a` vs `a / b` when popping), multi-digit number tokenizing, whitespace, integer division semantics, division by zero; parentheses: push `(`, unwind to `(` on `)` — or recursive descent, which reads better. Follow-up: unary minus.

**LC18. Implement a generic object pool: `T borrow(Duration timeout)` and `void release(T)`, max N objects, blocks up to the timeout when exhausted, creates objects lazily via a supplied factory.**
> **Hints:** `Semaphore(N)` guarding capacity + `ConcurrentLinkedQueue`/`BlockingQueue` of idle instances; `borrow`: `tryAcquire(timeout)` → poll idle queue → if empty, create via factory; `release`: return to queue *then* release permit (order matters); pitfalls: leaking permits when factory throws (release permit in catch), double-release by a buggy caller (track borrowed set or wrap in a handle), shutdown draining. Follow-ups: validation-on-borrow for stale connections, why real pools (Hikari) also need eviction/keepalive, try-with-resources friendly `PooledObject implements AutoCloseable`.

**LC19. Using a JDK dynamic proxy, implement `withRetry(T target, Class<T> iface, int attempts)` that returns a proxy retrying any failed method call — the mechanism behind Spring's `@Retryable`.**
> **Hints:** `Proxy.newProxyInstance(classLoader, new Class[]{iface}, handler)`; `InvocationHandler.invoke` loops attempts around `method.invoke(target, args)`; critical detail: `InvocationTargetException` must be unwrapped (`getCause()`) — retrying on the wrapper or rethrowing it wrongly is the classic bug; don't retry `equals`/`hashCode`/`toString`; only retry designated exception types; preserve the last cause. Follow-ups: why this needs an interface (JDK proxy limitation) and what CGLIB/ByteBuddy do instead; connect to why `@Transactional` self-invocation fails — same proxy mechanics.

**LC20. Build a mini validation framework with reflection: define `@NotNull` and `@Range(min, max)` annotations, then implement `List<String> validate(Object o)` that checks all annotated fields and returns violation messages.**
> **Hints:** Annotations need `@Retention(RUNTIME)` and `@Target(FIELD)` — forgetting retention is the #1 stumble; walk `getDeclaredFields()`, `setAccessible(true)`, check `isAnnotationPresent`, read annotation attributes for the range; collect messages with field name + expected vs actual; pitfalls: superclass fields (`getDeclaredFields` doesn't climb — loop `getSuperclass()`), primitive vs boxed handling for `@Range`, `IllegalAccessException` handling, modules/strong encapsulation caveat. Follow-ups: nested object validation (recursion + cycle guard), how Bean Validation does this at scale, and the annotation-processor/compile-time alternative.

**LC21. Task scheduler with dependencies: given tasks `A→[B,C]` meaning A depends on B and C, return a valid execution order, and detect cycles with a useful error message.**
> **Hints:** Topological sort — Kahn's algorithm (in-degree map + queue of ready tasks) or DFS with three colors (white/gray/black; gray-hit = cycle, and the gray stack gives the cycle path for the error message); Kahn's cycle detection: processed count < total; data-structure choice: `Map<String, List<String>>` adjacency; pitfalls: tasks that appear only as dependencies (never as keys), duplicate edges, deterministic ordering (use a sorted/priority ready-queue if required). Follow-up: extend to parallel execution — emit *levels* (tasks whose deps are all done can run concurrently) and relate to real systems (Gradle task graph, Airflow DAGs, `CompletableFuture` composition).

**LC22. Design an immutable `Money` class (amount + currency) with `add`, `multiply`, and an `allocate(int... ratios)` that splits an amount by ratios without losing or inventing cents — e.g., allocate $0.05 as 3:7.**
> **Hints:** `BigDecimal` (never double for money), `final` fields, operations return new instances; `add` must reject currency mismatch (throw, don't coerce); equals/hashCode: decide `2.50` vs `2.5` — normalize scale or use `compareTo` semantics consciously; **allocate is the meat**: naive per-share rounding loses pennies — compute floor shares in the smallest unit (cents), then distribute the remainder one cent at a time (largest-remainder method or round-robin), assert the parts sum exactly to the original; this is Fowler's classic Money allocation. Follow-ups: why `BigDecimal.equals` is a trap in tests (scale), storing money in the DB (integer minor units vs `NUMERIC`), and where rounding mode becomes a business decision (banker's rounding).
